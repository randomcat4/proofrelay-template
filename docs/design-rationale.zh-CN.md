# 这些门为何存在

[English](design-rationale.md)

ProofRelay 来自一次长期、多工作者研究协作的抽象：数学内容和协调系统都必须经受对抗式审查。领域专用主张被移除，反复出现的失效模式被转化为通用控制。

| 失效模式 | ProofRelay 控制 |
|---|---|
| 聊天看似活跃，但没有正式工作 | 用 Issue 持久认领和专用分支定义启动 |
| 投递接口报错不明确，可能造成重复提示 | 回读状态、只投递一次、监控幂等 |
| 多名工作者重复同一条诱人路线 | 路线注册、结构区分、每路线单一负责人 |
| 审查期间候选继续移动 | 绑定完整候选 commit |
| 验证者看过兄弟路线 | 披露隔离；受污染审查记为 `INCONCLUSIVE` |
| 作者或友好审查者实质自证 | 分离作者、维护者主审和验证者 |
| 长计算被误认成无限结论 | 强制分母、剪枝、覆盖字段与 `NO_HIT_NOT_A_PROOF` |
| 精确输出后来无法复现 | 提交源码、去敏收据、哈希和工件清单 |
| 部分定理被说成完整目标 | 冻结目标，并分别记录路线影响和顶层影响 |
| 正确、形式化和新颖被混为一谈 | 正交状态轴 |
| PR 合并被当作真值投票 | 合并保全工件；独立原子状态 PR 才接受主张 |
| 清理时失败记录消失 | 追加式来源链和取代式修订 |
| 频繁巡检淹没有用更新 | 安静监控，只在实质变化或需操作时通知 |

该设计优先保证公开主张保守、来源链可检查。当错误主张代价较高时，它有意接受一定流程成本。小项目可以减少验证人数，但若要合并角色或状态轴，应留下明确决策记录。
