# 协作纪律

[English](discipline.md)

以下规则构成 ProofRelay 的规范核心。

## 1. 唯一正式工作面

GitHub 保存任务、不可变输入、候选、证据、审查与接受状态。聊天可以通知链接或简短状态，但不能单独证明任务已启动、已完成或已被接受。

## 2. 先冻结再工作

每个工作单元都要固定目标版本、精确量词或验收标准、允许输入、预期输出、基准 commit、预算、最快证伪测试和停止条件。修改目标要建立新版本，不能悄悄改写当前任务。

## 3. 只认持久化启动证据

`PROMPT_SENT`、`ACTIVE` 或无人回复的消息都不算启动。通常只有 Issue 认领加专用分支等持久仓库工件出现后，才进入 `CLAIMED`。当任务可能已经送达时，监控器不得反复投递。

## 4. 一名负责人、一条通道、一个分支

每个活跃工作单元只有一名负责者和一个限定目录。并行路线必须结构不同，或明确说明它们是复现实验。工作者不得修改兄弟路线或已接受状态文件。

## 5. 仓库优先交付

完整论证、实现、日志、证书和收据必须进入仓库。Issue 评论与聊天回复保持简短，只指向 PR 或阻塞项。

## 6. 候选身份不可漂移

审计和验证绑定完整 commit SHA，而不是移动分支、PR 标题或“最新版”文件。修订产生新 commit，并可能需要重新验证。

## 7. 职责分离

候选作者、维护者主审和独立验证者是不同角色。作者不能认证自己的候选；验证者不能悄悄修补候选；只有维护者可以修改接受状态账。

## 8. 诚实记录隔离程度

验证必须记录验证者能看到哪些内容。使用 `STRICT_FRESH`、`CONTEXT_ISOLATED`、`CROSS_LANE` 或 `NOT_INDEPENDENT`；看到过兄弟路线时不能声称盲审或全新验证。隔离失败应给 `INCONCLUSIVE`，不能方便地判通过。

## 9. 对抗式验证

验证的目标是主动击破主张：重建定义、检查边界、审计等价变换与引用、用结构不同的实现复跑关键证据，并只给出 `CORRECT`、`INCORRECT` 或 `INCONCLUSIVE`。

## 10. 状态不能塌缩

主张真值、审查、计算、形式化、可复现性和新颖性是独立维度。例如：

- `PROVED_IN_CANDIDATE` 不等于 `ACCEPTED`；
- `MAIN_AUDIT_PASS` 不等于独立验证；
- `COMPUTATION_REPRODUCED` 不等于一般证明；
- `FORMALLY_CHECKED_PARTIAL` 不等于完整形式化；
- 新颖性 `NOT_ASSESSED` 不等于 `NOVEL`。

## 11. 有限证据必须有分母

每次搜索都报告理论全集、实际执行数、剪枝规则和完备性理由。除非另有证明表明有限全集完全覆盖目标，否则 `NO_HIT` 只是探针。

## 12. 收据是结果的一部分

计算任务记录源码 commit、精确命令、环境、起止时间、退出码、输入输出、哈希、资源使用和搜索分母，并去除远端基础设施细节。

## 13. 主审本身是独立工作

维护者要阅读承重论证、检查范围与引用、复跑相关证据、检查秘密边界并留下审计记录。自报信心或验证者标签不能替代这一门。

## 14. 状态原子更新

接受状态 PR 必须同时更新机器账与人读账，并链接冻结任务、候选 commit、候选 PR、主审、验证 PR 与收据。部分更新应被校验器拒绝。

## 15. 合并与真值是两件事

候选被合并可能只表示工件已保全。只有通过状态更新门才算接受。反过来，错误或被拒候选仍是有价值证据，必须保留版本。

## 16. 保留失败

不得删除反例、失败路线、收据不匹配或上下文污染报告。用新 commit 和明确来源链取代旧版本，不能把历史“打扫”得比真实过程更干净。

## 17. 监控要安静且幂等

联系工作者前先读取仓库状态。不打断正在生成的任务，不重发可能已经送达的消息，只报告实质变化、精确阻塞、完成的门或必须由人处理的动作。

## 18. 预算跟随证据

只有完整证明或证伪、经验证的严格部分结果、可复现反例或精确结构阻塞，才支持继续投入。文字长度、信心、重复无命中和沉没成本都不构成续费理由。

## 19. 权限与秘密保持最小化

工作者只取得该路线所需的权限和输入，不共享凭据，也不接触无关私人上下文。远端机器只运行固定 commit 的已提交代码，并返回去敏收据。

## 20. 公开主张保持保守

README 首先写顶层现状。正确性、完整性、新颖性和发表就绪程度分别陈述；限制和冲突应放在其限定的主张附近。
