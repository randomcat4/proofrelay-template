# 端到端工作流

[English](workflow.md)

## 角色

- **维护者：**冻结任务、控制接受状态、执行主审并处理治理冲突。
- **作者/工作者：**负责一条有边界的路线并提交候选；不能修改接受状态。
- **验证者：**接收绑定 commit 的验证包并给出有限裁决；不能验证自己的候选。
- **计算工作者：**运行已提交代码并返回去敏收据；无权超出任务范围解释结果。

同一人或系统可在不同工作单元承担多个角色，但不能同时作为同一候选的作者和独立验证者。

## 阶段 0 — 项目初始化

1. 替换模板标识并定义受保护分支。
2. 在 `contracts/frozen-target.md` 写精确目标。
3. 在 `state/PROJECT_STATE.json` 配置验证门槛。
4. 启用分支保护和必需 CI。
5. 根据 `config/labels.json` 建立标签。

## 阶段 1 — 冻结工作单元

建立 **Frozen work unit** Issue，写明不可变目标版本和基准 commit、精确范围与非目标、允许证据与禁止上下文、交付物与目录所有权、成功/部分成功/停止/预算条件、最快证伪测试、已知风险和隔离等级。

实质修改必须建立新版本或替代工作单元。

## 阶段 2 — 认领与启动

工作者只发一次认领评论，登记身份和分支，并创建 `work/<work-unit>-<handle>`。在持久仓库证据出现前，状态仍是 `START_PENDING`；推荐同时出现认领和分支后才转为 `CLAIMED`。

除非 Issue 明确要求独立复现，否则一个工作单元只允许一个活跃负责人。监控器不能把聊天在线状态当作启动证据。

## 阶段 3 — 候选交付

运行 `python scripts/new_work_unit.py attempt <work-unit> <handle>` 建立目录。候选至少包含：

- 写明精确状态与自包含论证的 `answer.md`；
- 记录来源和运行元数据的 `receipt.json`；
- 放程序的 `src/`；
- 放必要原始输出或紧凑证书的 `out/`。

候选 PR 绑定基准 commit，首行使用允许状态，不得修改接受状态账。

## 阶段 4 — 主审

维护者检查目标忠实性、量词、边界、等价变换、引用条件、一般论证与有限证据边界；在干净环境复跑承重计算，核对哈希与分母，检查隐私和权限，并用版本化审计记录 `MAIN_AUDIT_PASS`、`MAIN_AUDIT_FAIL` 或 `MAIN_AUDIT_INCONCLUSIVE`。

主审通过只会触发验证任务，不会直接接受主张。

## 阶段 5 — 独立验证

验证包只包含冻结目标、候选 commit 与明确允许的基线。验证 Issue 指定完整 SHA 和对抗清单。验证者使用 `verify/<work-unit>-<handle>` 和独立 PR。

发现关键缺口时，验证者只报告，不改写候选。作者可以提交新候选 commit；实质修订需要另一轮独立验证。

## 阶段 6 — 状态裁决

只有满足配置的证据门槛后，维护者才能用专门 PR 更新接受状态，并同时修改：

- `state/PROJECT_STATE.json`；
- `state/STATUS.md` 与 `state/STATUS.zh-CN.md`；
- 路线注册表；
- 证据变化时的工件清单；
- 变更日志。

状态项必须链接候选、主审、验证、收据和精确 commit。

## 阶段 7 — 监控或关闭

路线被接受、证伪、精确阻塞、超预算、被取代或不再值得投入时，应关闭或暂停。所有证据保留。把工作者复用于新任务时，必须建立新的自包含 Issue 并重新认领。

## 聊天回传契约

使用外部聊天时，要求最多三行非空内容：

```text
STATUS: <允许状态>
PR: <URL>
BLOCKER: <URL，仅需要时>
```

所有实质材料进入 GitHub。
