# 验收：代码、语义、阅读质量分别判断

## 验收对象

检查实际要交付的定理、模块和对应文档。使用 GitHub PR/Commit 原生版本定位即可，不创建额外哈希清单。
Review 期间候选变化时按 Git 差异重查受影响部分；旧 Review 不自动覆盖新 statement。

## 1. 机械检查

- 执行实际项目规定的依赖构建与目标检查，确认主定理在构建覆盖内；保存命令和结果到 PR/必要日志。
- 确认源码与依赖产物匹配，尤其是刚切换工作树或依赖源已更新。
- 对交付 theorem 检查传递依赖中的 `sorryAx`，不是只 grep 当前文件。用 `#print axioms Fully.Qualified.theorem`、项目既有检查器和真实 Lean 环境结果。
- 标准公理如 `propext`、`Classical.choice`、`Quot.sound` 按项目允许范围处理；新增/自定义公理和某些计算机制须显式核查，不能因为“没有 sorry”就放行。
- 普通 `lake build` 允许未完成证明以警告通过；图颜色、编译日志中的最后一行、源文件无 `sorry` 字符都不是独立完整性判据。
- `#print axioms` 若未执行，只能说明建议检查；不得编造输出。

代码检查工具能够检查的是形式对象；语义和研究价值不是它的职责。

## 2. 原文与证明范围

独立审查实际定义、参数、隐式实例、结论和原文对应。条件版本、特例、辅助引理与完整结果分开。
原文证明与替代证明分开说明。把来源结果放入新增假设不等于把它形式化了。
可复用经典结果的存在不自动说明新颖性；本 Skill 不据形式化通过宣称新定理或投稿就绪。

## 3. 人类可读性

审查结果页是否无需 Lean 背景也能识别对象、前提、结论、数学主线、关键引理和未覆盖范围。
检查 prose 对应的是实际 Lean statement，不是初始目标或作者愿望。
文档说一个结论已完成，而代码/依赖尚有占位，是实质缺陷。

## 4. 图与项目协作

路线图和真实 DAG 标题、边来源、过滤范围区分清楚。
Issue/PR 的完成范围与代码一致；CI 失败或 Review 争议没有被隐藏。权限不足和工具缺失不是数学错误。
同账号的 agent 审查意见不能伪装为另一人类 GitHub approval。

## 分项结论，不加状态数据库

在 PR 或交付说明用自然语言分别给出：

| 方面 | 示例结果 |
|---|---|
| Lean | 指定目标已实际构建且相关依赖检查通过 / 有占位 / 未运行 / 构建失败 |
| 原文一致性 | 匹配 / 明确条件性或其他差异 / 不匹配 / 材料不足 |
| 人类可读性 | 可独立阅读 / 有明确待修订项 / 未审 |
| 证明依赖 DAG | 已实际提取并说明范围 / 仅投影视图 / 未取得 |
| GitHub | PR 已创建待审 / 仅本地成果 / 具体权限阻塞 |

这些是报告维度，不是要求同步维护的枚举状态机。部分成果可以交付，但必须说明范围；不能靠多个维度投票凑“总 PASS”。

## 交付结构

先报结果和边界，再给数学结果页、Lean 声明与文件、实际构建/审查位置、路线图与可用 DAG、Issue/PR，最后列最小剩余工作。
没有未决问题不制造下一轮；没有授权不自动合并/公开。
