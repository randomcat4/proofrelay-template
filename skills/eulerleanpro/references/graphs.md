# 形式化路线图与 Lean 证明依赖 DAG

只把第二种叫 DAG。本文件规定语义，不创建新的图数据库或调度器。

## 形式化路线图

路线图是人/Agent 提出的数学计划：目标、承重引理、候选方案、替代路线、工作包、风险和前置材料。
它可含未证、失败、竞争方案；计划关系可以修订。GitHub Issue 的拆分与 blocked-by 也属于工作组织，不属于证明事实。
路线图可以是一页 Blueprint 或 Markdown。只链接 Issue/PR，不再复制负责人、任务状态和所有评论到一份中央账本。

## Lean 证明依赖 DAG

节点是实际声明；边 `A → B` 表示 A 的类型或 proof term 实际引用 B。最好分开类型/陈述依赖与证明体依赖。
来源应是当前构建对应的 Lean 环境/成熟提取工具，不是扫描源码中的名字、import 关系或 LLM 推测。
确有开发占位的声明可出现在“开发中依赖视图”，但必须标出未完成及继承的缺口，不得混同已验证的最终证明结构。

名字相同不证明对象相同，原文意义仍由语义审查负责。真实依赖图也不是人类证明的完整因果解释。

## 成熟工具怎么使用

优先项目已有的 Lean 环境提取器；其次可用 Verso Blueprint 的自动依赖信息，或既有 LeanArchitect/项目工具。按当前项目版本文档调用。
Verso 中手写 `uses` / `proofUses` 与自动推断可以共存、覆盖。普通 `vbp query uses` 输出不能无条件称真实 DAG：必须确认边的来源确为自动提取，保留陈述/证明轴，解释人工覆盖。
LeanArchitect 的 `uses`、`proofUses`、`sorry_using` 也可声明预期依赖，不能自动当作已证明的引用事实。

不能分离自动边与人工边时，只把现成图展示为“形式化路线图/混合蓝图”，同时说明实际 DAG 尚未取得。不为凑功能现场编一个正则解析器。

## 实际提取的最小操作顺序

1. 先对本轮目标和相关源依赖实际构建，不读取过时的导出。
2. 已选 Verso 项目先看本地帮助，再用 `lake exe vbp query node LABEL` 与 `lake exe vbp query uses LABEL` 查看声明关联和依赖。只接受实际标明自动提取的边；不知道来源时不猜。
3. 若尚未开启自动提取，在与项目版本兼容且已授权的文档变更中启用工具提供的 `autoDeps`，按当前手册核对作用范围；不要让人工 `uses` 覆盖后仍称纯自动图。
4. 既有 LeanArchitect 工程可用其 `#show_blueprint` 和 `lake build :blueprint`，仍逐项区分真实推断与手工 override/占位依赖。无需为用这些工具再写一个 extractor。
5. 导出并说明目标、边方向、类型/证明轴、所用工具和投影规则。代码改动后重新生成；不能稳定取得纯自动关系时交付路线图并明确实际 DAG 未取得。

## 可读的投影视图

通常不应向数学家展示所有内核细节。可以折叠无关辅助节点、过滤基础逻辑、将 Mathlib 当外部叶子，但标题必须写“Lean 证明依赖 DAG 的投影视图”。
说明：根定理、边方向、提取工具/命令、构建范围、过滤方式、是否截断及是否隐藏 Mathlib 传递依赖。图的大小上限与过滤可能隐藏关键内容，不能用它认证无遗漏。

StatLean 的示范提取器会过滤内部细节并设置节点上限；本包借鉴展示理念，不把这种显示图当作完整证明证书。
合并多个声明成一个显示节点可能人为形成环。遇到这种情况保留底层声明级视图，不把循环投影冒充严格 DAG。

## 不需要两套同步状态

唯一代码事实是 Lean 源及其当前构建；路线图是数学解释；GitHub 是协作事实。
自动依赖可重新生成，没必要由 agent 维护一份 `claim_ledger.json`。手工路线变化进入同一个 PR 的文档修改；构建刷新自动数据。

## 检查问题

- 这条边来自实际 proof term，还是作者预测？
- 显示的是陈述依赖、证明依赖还是 import？
- 是否在旧 `.olean` 上提取？
- 图被过滤/截断了吗？可见绿色是否掩盖未知依赖？
- 节点虽然不含本地 `sorry`，是否依赖未证 helper？

无法回答时报告图的限制，不通过修改标题制造确定性。
