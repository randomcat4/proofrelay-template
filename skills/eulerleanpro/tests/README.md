# 检查与验收：不要混淆三种事情

## A. 安装包结构检查（可直接执行）

```bash
python -m unittest discover -s tests -v
```

这些测试只读取本包，检查入口、相对链接、模块可达性、许可证、上游原文一致性和场景数据。仅用 Python 3.10+ 标准库，不访问网络，不调用模型，不运行研究控制器，不改用户项目。

## B. Skill 行为验收（本次尚未运行）

`acceptance-cases.json` 有 30 个场景，每项包含输入、预期行为和一票否决的错误。它不是 30 次模型测试的结果。
在真实 coding-agent 宿主中，复制本包并使用隔离测试项目，逐项给出输入与所需文件。记录实际工具调用、产物、权限动作和最终报告；不能只让同一模型为自己的输出打分。

建议先跑 E01/E03 的基础接入，再跑 E06/E08/E11/E12/E14/E18/E21/E24。其余覆盖边界和回归。
每项判定为通过、失败或未执行；任何 critical_failure 命中均失败。不按回答是否出现关键词判定，也不把“环境不具备”的真实说明算模型失败。

## C. Lean 与文档端到端检查（本次尚未运行）

在匹配工具链的 Mathlib 测试项目中运行 `examples/README.md` 的流程，再运行两个负例：

- `fixtures/AdmittedDependency.lean`：主定理无本地 sorry，但继承未证依赖；应被指出。
- `fixtures/PremiseSmuggling.lean`：把结论作为输入；内核不负责识别它与原无条件目标不同，语义审查必须发现。

负例故意含缺陷，只在隔离测试项目使用，不能作为交付库的一部分。
另用一个实际 Blueprint 工程测试现有版本命令、自动/人工边区分、可读文档构建、私有预览以及失败后的接手。实际项目/版本/命令和结果写入测试记录，不复制上游宣传数据。

## 维护时

每次修改触发条件、许可边界、图语义、独立性或验收规则，重跑相应场景。若只改排版，至少重跑结构检查。
包内 `VALIDATION.md` 只描述打包时真正执行的检查，不能当作未来所有项目的验收证明。
