# 重大结果形式化主流程

前置：目标和工程已定位；读 `references/statements.md`、`references/delegation.md`、`references/proving.md`、`references/readability.md`。

## A. 先定数学接口

形式化者从来源构造定义/陈述，语义审查者独立核对。先查 Mathlib 表示，避免重复开发已有数学。
重要未知列进对应结果的缺口，不通过添加假设偷偷解决。

## B. 路线图到工作包

协调者按承重引理和接口划分可审阅工作包。明确每项输入、输出、负责文件和依赖。
若未证目标需拆分，路线图可以改；原题不能暗改。工作状态使用 GitHub 原生功能，不写自制 scheduler。

## C. 按需并行

经审查的独立模块交不同证明者；共享定义由一名角色维护。真实宿主能力不足时降低并行而非假装启动。
子任务开始前接收完整任务单和必要引用；子任务返回实际文件/PR、命令结果、数学骨架与未完成 goal。
最终审查不由同一作者上下文完成。

## D. 编译与有意义的重规划

先窄目标试错，再集成。失败要分清语法/API 问题、类型/实例问题、helper 过强、来源缺口或反例。
因 Lean 实作困难可换证明；因数学目标改变需显性返回语义审查。不要无限重试一个已经失败的 tactic。
局部卡住时让其他独立任务继续。给出最小剩余义务而非用运行次数掩盖没有进展。

## E. 叙述同步生成

每项成果有数学陈述、假设对照与证明主线。叙述者可以先起草，但最终文字必须重新对照集成后的源码。
采用 Blueprint 时读 `references/blueprint.md`；已有数学说明可直接复用，不为了格式重写整本论文。

## F. 提取与审查

构建后用成熟工具提取真实依赖，按 `references/graphs.md` 区分手工边、自动边和投影。缺提取能力就明确未取得。
进入 `workflows/deliver.md`；任务 PR 始终保持实际的范围和未完成情况。
